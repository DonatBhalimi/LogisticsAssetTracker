# Data Model

## Document Purpose

This document defines the core data entities, fields, enums, nullability rules, relationships, and data integrity requirements for the Logistics Asset Tracker MVP.

It should guide database design, backend models, DTOs, and API planning.

Unless a field is marked nullable, it must be treated as required.

Detailed movement validation, suspicious rules, thresholds, API behavior, and UI behavior are defined in Documents 05, 06, and 07.

---

## User

## Fields

- id
- fullName
- email
- passwordHash
- role
- isActive
- createdAt
- updatedAt

## Rules

- email must be unique.
- email uniqueness must be enforced case-insensitively.
- passwordHash must never be exposed through API responses.
- inactive users must not be allowed to log in.

## Role Values

- Admin
- Manager
- Operator

- Truck

## Asset

## Fields

- id
- assetCode
- name
- type
- currentLocationId
- status
- condition
- assignedToUserId nullable
- qrCodeValue
- isActive
- createdAt
- updatedAt

## Purpose

Stores the current state of each logistics asset.

Status and condition must be stored separately.

`assignedToUserId` is informational metadata only in the MVP.

It does not control visibility or permissions.

## AssetCode Rules

- assetCode must be unique.
- assetCode must be immutable after creation.
- assetCode uniqueness must be enforced case-insensitively.
- assetCode must be generated or controlled by the backend.

## QR Code Rules

`qrCodeValue` stores a permanent unique opaque token.

Rules:
- qrCodeValue must be unique.
- qrCodeValue must be immutable.
- qrCodeValue must be generated by the backend.
- qrCodeValue must not be accepted as a user-selected value.
- qrCodeValue must not depend on editable asset information.

The QR code should point to a URL using this token.

Example:
- `/assets/qr/{qrCodeValue}/update`

## AssetType Values

- Pallet
- Crate
- Box
- Container
- Tool
- Device
- WarehouseEquipment

## Status Values

- Available
- InTransit
- Delivered
- Lost
- Retired

## Condition Values

- Good
- Damaged
- NeedsInspection

## Retired and isActive

`Retired` is a business lifecycle status.

Retired is terminal in the MVP.

Retired assets cannot receive normal movement updates.

`isActive = false` is administrative deactivation.

Inactive assets cannot receive new movement updates.

## AssetMovement

## Fields

- id
- assetId
- fromLocationId
- toLocationId
- previousStatus
- newStatus
- previousCondition
- newCondition
- sourceType
- updatedByUserId
- notes nullable
- isSuspicious
- suspiciousReason nullable
- createdAt

## Purpose

Stores every completed state-changing update to asset location, status, or condition.

Movement history is append-only during normal use.

Asset creation does not create an AssetMovement.

Movement history begins with the first post-creation movement update.

## Movement Creation Rules

At least one of location, status, or condition must change for AssetMovement to be created.

Notes-only or no-change submissions must not create AssetMovement.

Invalid movement attempts must not create AssetMovement and must not update Asset.

Invalid attempts are recorded through AuditLog.

## Location Storage Rules

If location changes:
- fromLocationId stores the previous location,
- toLocationId stores the new location.

If only status or condition changes:
- fromLocationId stores the current asset location,
- toLocationId stores the same current asset location.

## SourceType Values

MVP allowed values:
- Manual
- QR

GPS is future scope and must not be implemented or accepted as an MVP SourceType.

## Notes Rules

`notes` is nullable for normal movement updates.

`notes` is required for:
- Manager/Admin inspection clearance,
- Manager/Admin direct Lost reactivation,
- Admin Lost-to-Retired,
- final movement created from approved Lost-reactivation request.

For approved Lost-reactivation, AssetMovement.notes must preserve MovementApproval.requestReason.

Manager/Admin decision notes remain on MovementApproval and relevant AuditLog metadata.

## Suspicious Field Rules

If `isSuspicious = true`, `suspiciousReason` must not be null.

If `isSuspicious = false`, `suspiciousReason` should be null.
Blocked attempts are marked suspicious only when an explicit rule from Document 05 matches.

## MovementApproval

## Fields

- id
- assetId
- requestedByUserId
- decidedByUserId nullable
- requestedLocationId nullable
- requestedStatus
- requestedCondition
- requestedSourceType
- approvalStatus
- requestReason
- decisionNote nullable
- createdAt
- decidedAt nullable

## Purpose

Stores approval requests for sensitive movement behavior.

In the MVP, MovementApproval is used only for Operator Lost-to-Available reactivation requests.

The asset remains Lost while approval is pending.

Approved requests create the final AssetMovement.

Damaged or NeedsInspection to Good does not use MovementApproval.

It is handled through Manager/Admin permission.

## Approval Data Rules

requestReason is required.

When a Lost-reactivation request is created, submitted movement notes must be stored as requestReason.

When approved, the final AssetMovement.notes must preserve requestReason.

requestedSourceType must be preserved when the final movement is created.

A QR reactivation request must ultimately create a QR movement, not a Manual movement.

A null requestedLocationId means the asset keeps its current location.

An asset may have at most one Pending Lost-reactivation approval at a time.

Direct Manager/Admin Lost reactivation must be rejected if a Pending Lost-reactivation approval already exists for the asset.

## ApprovalStatus Values

- Pending
- Approved
- Rejected

## Approval State Rules

For Pending approval:
- decidedByUserId must be null,
- decidedAt must be null,
- decisionNote may be null.

For Approved or Rejected approval:
- decidedByUserId must not be null,
- decidedAt must not be null,
- decisionNote must not be null.

MovementApproval may be updated only to record its decision.

It must not be deleted during normal use.

## RiskRecommendation

## Fields

- id
- assetId
- riskLevel
- riskType
- reason
- recommendation
- generationSource
- modelName nullable
- generatedByUserId nullable
- createdAt

## Purpose

Stores rule-based and AI-assisted risk recommendations.

Risk detection is rule-based first.

AI may explain or improve the recommendation, but AI must not update asset data directly.

If no risk is detected, no RiskRecommendation record is created.

If multiple risk types are detected, the MVP creates one RiskRecommendation record per detected risk type.

Old recommendations remain historical and must not be overwritten.

## RiskLevel Values

- Low
- Medium
- High
- Critical

Low is reserved for future lower-severity rules.

MVP risk rules currently produce Medium, High, or Critical.

## RiskType Values

- DelayRisk
- NoRecentUpdate
- DamagedAsset
- LostAsset
- SuspiciousMovement

## GenerationSource Values

- RuleEngine
- RuleEngineWithAI

RuleEngine means deterministic rule-based explanation or fallback.

RuleEngineWithAI means rules detected the risk and AI generated or improved the explanation.

modelName must be null for RuleEngine.

modelName must be non-empty for RuleEngineWithAI.

generatedByUserId is the authenticated user for on-demand analysis.

It may be nullable only for system-initiated analysis.

## AuditLog

## Fields

- id
- userId nullable
- action
- entityType
- entityId nullable
- metadataJson nullable
- createdAt
- isSuspicious
- suspiciousReason nullable

## Purpose

Stores completed actions and blocked attempts for traceability.

Audit logs are visible to Admin and Manager.

userId may be nullable for system-generated actions.

metadataJson may contain relevant request details, previous values, attempted values, rejection reason, suspicious reason, approval reason, decision note, or retirement note.

metadataJson must not store:
- passwords,
- password hashes,
- JWT tokens,
- API keys,
- secrets.

AuditLog records are append-only during normal use.

---

## Computed Values

Delayed is not stored as AssetStatus.

Delayed is a computed risk or dashboard signal.

Risk thresholds and stale calculations are defined in Document 05.

---

## Deletion and Referential Integrity

Users, Locations, and Assets referenced by historical records must not be physically deleted during normal use.

They must be deactivated using isActive.

Foreign-key relationships from AssetMovement, MovementApproval, RiskRecommendation, and AuditLog must not cascade-delete historical records.

AssetMovement, RiskRecommendation, and AuditLog records are append-only and must not be edited or deleted during normal use.

---

## Relationships

- Asset.currentLocationId references Location.id.
- Asset.assignedToUserId references User.id and is nullable.
- AssetMovement.assetId references Asset.id.
- AssetMovement.fromLocationId references Location.id.
- AssetMovement.toLocationId references Location.id.
- AssetMovement.updatedByUserId references User.id.
- MovementApproval.assetId references Asset.id.
- MovementApproval.requestedByUserId references User.id.
- MovementApproval.decidedByUserId references User.id and is nullable.
- MovementApproval.requestedLocationId references Location.id and is nullable.
- RiskRecommendation.assetId references Asset.id.
- RiskRecommendation.generatedByUserId references User.id and is nullable.
- AuditLog.userId references User.id and is nullable.
- One Asset has many AssetMovements.
- One Asset can have many MovementApprovals.
- One Asset can have many RiskRecommendations.
- One User can update many AssetMovements.
- One User can request or decide many MovementApprovals.
- One Location can contain many active Assets.
