# Testing and Acceptance Criteria

## Document Purpose

This document defines what must work before the MVP is considered demo-ready.

It does not redefine business rules, API behavior, database schema, UI behavior, or AI logic.

Testing must follow Documents 02 through 10 as applicable.

---

## Phase 1: Project Setup

Acceptance criteria:

- Backend runs locally.
- Frontend runs locally.
- PostgreSQL connection works.
- Entity Framework Core is configured.
- Folder structure is clear.
- Initial README exists.
- QR generation and QR scanning library decisions are recorded.

---

## Phase 2: Core System

Acceptance criteria:

- User can log in and log out.
- Role-based navigation works.
- Restricted pages block unauthorized users.
- Inactive users cannot log in.
- Admin can manage users.
- Admin can create, edit, and deactivate locations.
- Admin can create, edit, view, and deactivate assets.
- Asset code and QR token are generated by the backend.
- Edit Asset does not expose movement-controlled fields.
- Basic audit logging exists for important actions.

---

## Phase 3: Basic Tracking

Acceptance criteria:

- QR code is generated for an asset.
- QR scan opens the correct movement page.
- Manual asset-code fallback works.
- Manual movement creates movement history with `sourceType = Manual`.
- QR movement creates movement history with `sourceType = QR`.
- Previous and new values are stored correctly.
- Inactive assets cannot receive movement updates.
- Admin and Manager can view or generate asset QR codes.
- Operator can scan QR codes but cannot manage QR generation.
- Inactive locations cannot be selected as destinations.
- Notes-only or no-change movement requests are rejected.
- Users cannot choose `sourceType`.

---

## Phase 4: Rules, Approvals, Suspicious Activity, and Audit

Acceptance criteria:

- Available to Delivered is blocked.
- Valid Available to InTransit to Delivered flow works.
- A movement changing status to Available requires resulting condition Good.
- A condition-only damage report may keep the current status unchanged.
- A movement may change Available to InTransit while also setting condition to Damaged or NeedsInspection when the pre-movement condition is Good.
- An asset already Damaged or NeedsInspection before the request cannot transition to InTransit or Delivered until cleared to Good.
- Operator cannot clear Damaged or NeedsInspection back to Good.
- Manager/Admin can clear condition to Good through manual movement.
- Inspection clearance without notes is rejected.
- QR endpoint cannot be used for inspection clearance.
- Retired assets cannot receive normal movement updates.
- Invalid movement leaves Asset unchanged.
- Invalid movement does not create AssetMovement.
- Invalid movement creates AuditLog.
- Operator Lost-to-Available creates an approval request when valid.
- Asset remains Lost while approval is Pending.
- Duplicate Pending approval is rejected.
- Approval and rejection without decisionNote are rejected.
- Manager/Admin can approve or reject Lost reactivation.
- Approved QR reactivation creates AssetMovement with `sourceType = QR`.
- Manager/Admin direct Lost reactivation works through the dedicated endpoint.
- Normal manual and QR endpoints reject Manager/Admin direct Lost-to-Available.
- Direct Lost reactivation is rejected while a Pending approval exists.
- Lost-to-Retired is Admin-only and manual-only.
- Suspicious completed movements are marked.
- Suspicious blocked attempts are logged.
- Suspicious Activity combines completed movements and blocked attempts.
- Audit Logs page is viewable by Admin and Manager.

---

## Phase 5: Dashboard and AI Risk Recommendations

Acceptance criteria:

- Dashboard counts are correct for active assets.
- Assets by status, condition, and location display correctly.
- Recent movements display correctly.
- Suspicious activity displays correctly.
- Pending approvals display correctly.
- Rule-based risk detection works.
- SuspiciousMovement risk follows the scope defined in Document 05.
- No-risk result does not create a RiskRecommendation record.
- On-demand analysis creates one recommendation per detected risk type.
- Mocked AI response is validated before saving.
- AI failure does not crash the app.
- Rule-based fallback recommendation appears when AI fails.
- Generated recommendations create AuditLog.
- AI does not approve, update, or override business rules.

---

## Phase 6: Final Quality

Acceptance criteria:

- Main user flows work.
- Role-based access works.
- QR flow works.
- Movement rules work.
- Approval flow works.
- Dashboard works.
- AI recommendation flow works.
- UI shows loading, empty, success, and error states.
- README is complete.
- Demo data exists.
- Screenshots are added if useful.
- No unfinished feature is presented as complete.

---

## Final Demo Checklist

The demo should show:

1. Login as Admin.
2. Create a location.
3. Create an asset with status Available and condition Good.
4. View asset details.
5. Generate or view the QR code.
6. Scan the QR code.
7. Create a QR location update.
8. Show movement history.
9. Create a manual location update.
10. Try an invalid Available-to-Delivered movement.
11. Show the backend error and unchanged asset.
12. Create a valid Available-to-InTransit movement while changing condition from Good to Damaged in the same request.
13. Try changing the Damaged asset to Available.
14. Show the blocked rule and suspicious attempt.
15. Clear condition back to Good as Manager/Admin through manual movement.
16. Mark the asset as Lost.
17. Log in as Operator.
18. Request Lost reactivation.
19. Show the asset remains Lost while approval is Pending.
20. Log in as Manager/Admin.
21. Generate a risk recommendation while the asset is Lost.
22. Show the saved LostAsset recommendation.
23. Approve the reactivation request.
24. Show the updated asset state and movement history.
25. Confirm the approved movement preserved the requested source type.
26. Show the Suspicious Activity page.
27. Show the Audit Logs page.
28. Show the Dashboard.

---

## Final Acceptance Rule

The MVP is accepted only if:

- backend rules are enforced,
- invalid actions do not change protected state,
- frontend displays backend outcomes clearly,
- main demo flow works,
- documentation matches implementation,
- no fake or unfinished features are presented as complete.
